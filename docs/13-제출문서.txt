[2] AI 활용 방식 및 결과 — 제출용 본문 (499자 / 500자, 공백 포함)

🔴 첫 문장에 "전 과정이 AI입니다" 라고 쓰지 않는다. 사실이 아니고, 뒤 문장들이 전부
   "AI 가 하지 않는 것"(개수는 SQL · 초는 타임스탬프 · 시작점은 코드)을 말하므로 자기모순이다.
   경계를 먼저 긋고 시작하는 편이 심사에서 더 강하다.

아래 한 문단을 그대로 복사해 붙인다.

시청자 질문에서 답 구간을 찾아 30초 숏폼으로 자릅니다. 이해와 판단은 AI가, 세고 자르는 일은 코드가 합니다. 전사는 whisper small에 도메인 어휘를 초기 프롬프트로 주고, 메모리가 길이에 비례해 무음에서 균등 분할합니다. Gemini 임베딩 코사인 0.85로 질문을 묶고 LLM으로 작명합니다. 답 구간 검색은 임베딩 top-k였다가 정답이 44개 중 29위라서 호출 수 그대로 LLM이 고르게 바꾸니 답 못 하던 질문이 클립이 됐습니다. 생성은 구조화 출력, 답변당 LLM 5회로 후보 3종을 LLM-as-judge가 겨룹니다. 흩어진 답은 브릿지 카드로 잇습니다. 모델이 말한 초 대신 전사 타임스탬프를 쓰고, 지시어로 시작하면 코드가 시작점을 당깁니다. 전사와 구간은 캐시해 질문마다 재사용합니다. 실행은 고정 DAG이라 에이전트 프레임워크가, 관측은 Langfuse가, 검색은 벡터 DB가 과해서, 단계·모델·토큰·지연을 남기는 테이블 하나로 질문당 단가를 실측합니다.

메모리가 길이에 비례해 균등 분할
  whisper 는 전사 길이에 비례해 메모리를 쓴다. 실측(2026-09-06): 30분 청크가 1.4GB,
  95분을 한 번에 돌리자 컨테이너 한도 2.93GB 를 넘겨 OOM(exit 137) 으로 죽었다.
  한도를 올리는 것은 답이 아니다 — 운영이 4GB VM 이다. 그래서 25분 상한으로 자른다.
  나누는 규칙은 둘이다. 상한을 넘지 않는 최소 개수로, 그리고 균등하게.
  95분을 30분 상한으로 나누면 30/30/30/5 가 아니라 24×4 다 — 마지막만 짧으면
  그 조각만 빨리 끝나 진행률이 거짓말을 한다. 경계는 목표 근처의 무음 한가운데로 당긴다.
  고정 길이로 자르면 문장 한복판에서 끊겨 그 발화가 양쪽 청크에서 모두 반토막 난다.
  근거: pipeline/ingest.py plan_chunks, config.py SHORTS_CHUNK_MAX_SEC

답 구간 검색을 임베딩에서 LLM 으로 바꿨다
  아래 [4] 절 전체가 이 한 문장의 근거다.

흩어진 답을 브릿지 카드로 잇는다
  Q&A 의 답은 한 덩어리로 있지 않다. A~B 와 C~D 를 이어 붙이고 사이에 0.4초 검은 카드로
  "45:26에서 이어집니다" 를 넣는다. 점프를 숨기지 않고 읽히게 만드는 쪽이 정직하다.
  자막은 같은 파일에 넣고 두 번째 조각 자막은 첫 조각 길이 + 브릿지만큼 뒤로 민다.
  실측: 조합 클립 18.93초 · 1080×1920 · clip_parts 2행.
  근거: adapters/ffmpeg.py, pipeline/subtitles.py build_part_cues

지시어로 시작하면 코드가 시작점을 당긴다
  프롬프트에 "지시대명사로 시작하지 않는다" 가 이미 있었는데 모델이 지키지 않았다.
  "저희는 이런 서비스들을...", "이렇게 수많은 AI 프로젝트들이..." 로 시작한 후보 셋이
  전부 자립성 판정에서 떨어졌다. 그래서 코드가 당긴다. 좋은 시작점의 뜻은 둘이다 —
  앞을 가리키지 않고, 앞 발화가 문장을 끝냈을 것. 두 번째 조건이 없으면 지시어만 피하다
  문장 한복판에 떨어진다(실측에서 "해나가고 있고" 에서 시작했다).
  자리를 못 찾으면 그냥 둔다. 30초 예산을 넘기면 당기지 않는다 — 앞머리만 붙고 답이
  반이 된 클립보다 시작이 어색해도 답이 온전한 편이 낫다.
  근거: pipeline/cutting.py lead_in

large-v3 를 버린 이유 (본문에서 뺐다. 물어보면 말한다)
  make_shorts.md 7절 실측표(2026-08-29, M계열 Mac · CPU · int8 · 5분 오디오 · language=ko).
  small + initial_prompt 는 9.4x 실시간 · 고유명사 오류 0회 · 추론 중 1.11GB.
  large-v3 는 0.9x 실시간 · 3.4GB · 니체를 닐체로 4회, 칸트를 칸토로 1회 흘렸다.
  large-v3 를 쓰면 4GB VM 에 들어가지도 않는다.

코사인 0.85 · 768차원
  config.py 의 SHORTS_CLUSTER_THETA, SHORTS_EMBED_DIM.
  768 은 3072 대비 저장이 1/4 이고 짧은 한국어 질문끼리의 유사도 순위는 거의 같다.
  저장 전에 정규화한다 — 3072 이 아닌 차원은 정규화되지 않은 벡터로 오기 때문이다.

역할 분담: 작명은 LLM, 소속은 임베딩, 개수는 SQL
  answers/clusters.py 머리 표. LLM 에게 인덱스를 맡기면 없는 번호를 대거나 빠뜨리고,
  개수는 세다가 틀린다. 기계가 정확한 일은 기계에 맡긴다.

답변 한 건에 LLM 5회
  config.py 의 SHORTS_ANSWER_CANDIDATES=3. 후보가 하나 늘면 judge 호출이 하나 는다.
  후보 셋은 서로 다른 방식이다 — 단일 구간, 흩어진 답의 조합, 핵심만 짧게.
  judge 는 영상이 아니라 텍스트를 보므로 렌더 전에 판정할 수 있다. best-of-3 가 싼 이유다.

모델이 말한 초는 쓰지 않는다
  CLAUDE.md 규약과 pipeline/cutting.py. 시각은 자막·발화 타임스탬프에서 되찾고,
  구간 번호는 화이트리스트로 검증하고, 30초 예산은 코드가 강제한다.
  프롬프트로 "지시대명사로 시작하지 마라"고 해도 모델이 지키지 않았다 — 그래서 코드가 당긴다.

중립 자산 캐시
  tease.md 4-1절. Source-Chunk-Segment 는 영상당 1회(전사 + 분할, 비싸고 느리다),
  Run 은 기준마다 1회(rank, 수 초). 기존 숏폼 툴의 "요청 건당 AI 호출" 대비 구조적 우위다.

관측은 Langfuse 가 과했다 — 테이블 하나만 직접 넣었다
  stage_calls 한 테이블이다. 컬럼은 stage · model · input/output/thinking/total/cached 토큰 ·
  latency_ms · params · error 다. LLM 뿐 아니라 STT·렌더·다운로드·미리보기까지 전부 남긴다
  (stage CHECK 로 값을 고정해 오타가 집계를 조용히 쪼개지 못하게 했다).
  thinking 토큰은 출력 단가로 과금되므로 따로 센다. params 에는 그 단계를 무엇으로 돌렸는지를
  남긴다 — stt 면 initial_prompt 와 vad, LLM 이면 프롬프트와 원본 응답. 없으면 재현이 안 된다.
  이걸로 질문당 단가가 실측으로 나온다(pricing.py).

  왜 Langfuse 를 안 썼나: 필요한 것은 단계별 토큰·지연·파라미터를 남기고 그걸 SQL 로 집계하는
  것뿐이었다. 트레이스 뷰어·프롬프트 관리·평가 워크플로·별도 서버는 이 규모에 과하고,
  4GB VM 에 컨테이너를 하나 더 올리는 값이 든다. 대신 이 파이프라인은 LLM 이 아닌 단계
  (STT · 렌더 · ffmpeg)가 시간의 대부분을 먹는데, 범용 LLM 관측 도구는 그쪽을 안 본다.
  이 제품의 실제 제약은 비용이 아니라 시간이라 그게 결정적이었다.
  마이그레이션 001_baseline.sql 215~245행.

벡터 DB 를 안 쓴 이유
  answers/embeddings.py 머리 주석. 세그먼트 수백 · 질문 수백 규모에서 numpy 브루트포스가
  1ms 밑이다. 수만 개가 되면 pgvector 를 켠다 — DB 가 Postgres 라 확장 하나면 된다.

에이전트가 아닌 이유
  answers/answer.py · judge.py 머리 주석. 다음에 뭘 할지 정하는 주체가 없는 고정 DAG 다.
  경계가 있는 판정 하나다. 정확한 용어가 심사에서 더 강하다.


[4] 검색이 임베딩으로 안 됐던 이야기 — 물어보면 이것을 말한다

원래 답 구간 좁히기는 임베딩 top-k 였다. 실측(2026-09-09)에서
"개발 직군의 주요 기술 스택은?" 질문에 대해 실제 답이 담긴 구간이 44개 중 29위와 30위였다.
1위는 글자만 겹치는 "기술 문화" 였다. 전체가 0.502~0.755 의 좁은 띠에 몰려 있어서
최소 유사도 임계값이 한 번도 아무것도 거르지 못했다.
top_k 를 늘려서 될 일이 아니었다 — 29위를 넣으려면 44개 중 30개를 보내야 하고,
그건 좁히기를 안 하는 것과 같다.

그래서 고르는 주체를 임베딩에서 LLM 으로 바꿨다. 구간 요약 전부를 주고 번호로 고르게 한다.
호출 수는 늘지 않았다 — 이미 경로 판정으로 LLM 을 한 번 쓰고 있어서 같은 호출에 얹었다.
이 변경으로 그 질문이 답변 불가에서 실제 조합 클립(18.93초, 2조각)으로 관통했다.
근거: update_plan.md M5 실측 1·2
