## 1. 콘텐츠 전제 ⭐

**이 문서에서 가장 중요한 절.** 아래 전제가 나머지 설계의 90%를 결정한다.
전제가 바뀌면 파이프라인을 다시 설계해야 하므로, 바꿀 때는 이 절을 먼저 고친다.

### 1-1. 단계

| 단계 | `content_type` | 대상 | 상태 |
|---|---|---|---|
| 1단계 | `LECTURE` | 인문학 강연 등 토크 영상 | **지금 여기** |
| 2단계 | `FILM` | 영화 (외국어) | 설계만 되어 있음 |

**두 단계는 같은 파이프라인의 두 전략이다.** `[1] 대사 확보`·`[5] rank`·`[6] 구간 잘라내기`·
`[7] 렌더`는 공유하고, `[2] 샷 검출`·`[3] 구간 분할`·`[4] 영상 해설`만 갈라진다(§4).

### 1-2. 1단계 — 강연

| 항목 | 전제 | 파생되는 설계 |
|---|---|---|
| 원본 | 한국어 강연 (유튜브) | 번역 불필요, STT 정확도 유리 |
| 길이 | 60~90분 | v1 은 앞 30분만. 청크는 1개 |
| 화면비 | 16:9 가로 | **리프레이밍 필요** |
| 자막 | 사람이 만든 자막 없음 · 자동자막은 사용 불가(실측) | **STT 가 주 경로** |
| 카메라 | 고정 1~2대, 컷이 거의 없음 | **샷 검출이 무의미** → `[2]` 생략 |
| 화면 정보 | 발표자 + 슬라이드, 30분 내내 동일 | **영상 해설이 정보를 안 만든다** → `[4]` 생략 |
| 구간 길이 | 주제 단위 3~8분 (추정, §9-7) | 구간 내부에서 30~60초 잘라내기 필요 |
| 자립성 | 논지가 그 자리에서 완결되는 경우가 많음 | **영화보다 쉽다** — v1 최대 리스크가 완화됨 |
| 권리 | 유튜브 표준 라이선스 추정 | 🔴 **운영 사용 전 권리 확보 필요** (§9-5) |

> **자동자막 실측 (2026-08-29)**: 대상 강연에는 수동 자막이 없고 자동자막만 있다. 텍스트가
> 깨질 뿐 아니라(`오 오 오 오`, `000`) **타임스탬프가 롤링 윈도로 서로 겹친다**
> (1번 `00:01.7→00:20.9`, 2번 `00:04.2→00:25.7`). §4-[6] 이 요구하는 "발화 경계 스냅"의
> 입력으로 쓸 수 없는 형태다. STT 가 대안이 아니라 유일한 경로다.
> 자동자막 파일은 STT 품질 비교용 기준선으로만 보관한다.

### 1-3. 2단계 — 영화 (설계 보존)

| 항목 | 전제 | 파생되는 설계 |
|---|---|---|
| 원본 | 영화 (외국어) | 회차 개념 없음 → 클리프행어 대신 "단독 성립" 중심 |
| 길이 | 30분 청크로 잘라서 입력 | 2시간 통짜는 다루지 않음 |
| 화면비 | 16:9 가로 | 리프레이밍 필요 |
| 자막 | 별도 파일(SRT) 또는 없음 | 프레임에 안 박혀 있음 → 무음 클립 트릭 사용 불가 |
| 씬 길이 | 1.5~4분 (숏드라마의 4~6배) | **씬 이어붙이기 불가**, 씬 내부 구간 잘라내기 필요 |
| 권리 | 개발 초기는 퍼블릭 도메인 | Internet Archive 등 |

### 1-4. 강연으로 시작할 때 쌓이는 것 / 안 쌓이는 것

**정직하게 적어둔다.** 강연은 그릇을 완성시키지만 영화의 어려운 알맹이는 남겨둔다.

| 쌓인다 (영화에 그대로 감) | 안 쌓인다 (영화에서 새로 짬) |
|---|---|
| 인프라 전부 — 레포·DB·잡큐·`stage_calls`·CLI/API·배포 | `[2]` 샷 검출 |
| `[1]` 대사 확보 (STT/SRT 파싱) | `[3]` 구간 분할 로직 (텍스트 ↔ 샷+자막공백) |
| `[5]` rank 구조 (고정 관문 + 가변 기준) | `[4]` 영상 해설 (Files API·해상도·오디오 토큰 노하우) |
| `[6]` 구간 잘라내기 · `[7]` 리프레이밍/렌더 | 영화 자립성 판정 (§9-2, 여전히 최대 리스크) |
| 중립/주관 분리 · O/X 품질 루프 | |

### EchoCut 에서 그대로 가져오지 **않는** 것

- **무음 클립 + "들리는 대사를 옮겨라"** — 자막이 프레임에 박혀 있다는 전제에 의존. 여기선 성립 안 함
- **후킹 씬 + 사이 씬 전부 + 클리프행어 씬 구조** — 구간이 길어서 두 개만 붙여도 6분
- **프레임 전량 투입 씬 검출** — 30분이면 1800프레임 ≈ 46만 토큰. 강연에선 아예 불필요
- **K8s Job / S3 체크포인트 / 3단 폴백 / 증분 판정** — 44편 규모의 답. 지금은 이르다

### EchoCut 에서 가져오는 것

1. **중립/주관 분리** (§3) — 콘텐츠 무관하게 성립. 첫날에 넣으면 공짜, 나중에 넣으면 마이그레이션
2. **프롬프트 지시보다 입력 제한** — "고르지 마라"고 지시하지 말고 아예 안 보여준다
3. **프레임 파일명 = 타임스탬프** — LLM 타임스탬프는 1~3초 어긋난다. 초 정밀도는 항상 파일명/자막에서
4. **자립성 관문을 감점이 아니라 후보 제외로** — 감점으로 두면 모델이 실제로 안 뺀다

## 3. 아키텍처 원칙 — 중립 vs 주관

**모든 판정 결과에 대해 "이건 사실인가 의견인가"를 먼저 답하고 저장 위치를 정한다.**

```
Source (원본 영상)
├── Chunk (분할 조각 — LECTURE 는 1개)
│   └── Segment ──────────── 중립 자산
│         ├── start_sec / end_sec
│         ├── description       (LECTURE: 주제 요약 / FILM: 화면 해설)
│         ├── dialogue          (STT/자막 원문)
│         └── (signals)         ← 나중에 추가할 수치 트랙 자리
│
└── Run (뽑기 1회) ────── 주관
      ├── criteria_prompt      (기준 프롬프트)
      ├── ranked               (순위·점수)
      └── Clip (완성 클립)
```

**중립** = 사용자 의도와 무관한 사실. 한 번 만들면 Run 이 몇 개든 재사용.
**주관** = 어떤 기준으로 무엇을 뽑을지. Run 마다 다름.

### 왜 이게 v1부터 필요한가

비용이 아니라 **개발 속도** 때문이다. rank 프롬프트를 튜닝하면서 매번 STT/분할을
다시 돌리면 한 번에 수 분씩 날아간다. 중립 자산을 DB 에 캐시해두면 rank 만 몇 초에 재실행된다.

### ⚠️ description 은 기준 중립적으로 써야 한다

여러 기준 프롬프트를 돌리려면(§6-2) description 이 모든 기준을 먹여 살려야 한다.
**description 프롬프트에 특정 기준을 넣는 순간 그건 중립 자산이 아니다.**

### ⚠️ Segment 는 rank 의 화이트리스트다

강연은 텍스트만으로도 rank 가 가능하므로 "구간 분할 없이 트랜스크립트에서 바로 30초를
고르게 하면 되지 않나"는 반론이 성립할 것처럼 보인다. **안 된다** — 그러면 모델이
타임스탬프를 자유 서술로 뱉고, 그 초는 믿을 수 없다(§12).

Segment 를 먼저 만들어 두면 rank 는 **존재하는 ID 중 하나를 고르는 문제**가 되고,
출력 검증이 가능해진다. 이게 `[3]`을 생략하지 않는 이유다.

## 4. 파이프라인

### 4-1. LECTURE (1단계 — 지금 구현하는 것)

```
60~90분 강연 (v1 은 앞 30분)
  │
  ├─[1] STT (faster-whisper) ─────── LLM 0회, word-level 타임스탬프
  ├─[2] 샷 검출 ─────────────────── 생략 (컷이 없다)
  └─[3] 주제 단위 분할 (LLM, 텍스트) ── ★ LLM 호출이 여기로 이동
        ↓ Segment 행 생성 (start/end + 주제 요약)
  ─[4] 영상 해설 ────────────────── 생략 (화면에 정보가 없다)
  ─[5] rank ─────────────────────── 기준 프롬프트로 1개 선정
  ─[6] 구간 잘라내기 ─────────────── 구간 안에서 30~60초. 발화 경계로 스냅
  ─[7] 리프레이밍 + 렌더 ──────────── 9:16 블러 레터박스, 원본 화질
        ↓
  clip_01.mp4
```

**LLM 호출 2회**(분할 + rank, `[6]`까지 3회). 30분 처리에 센트 단위 · 수 분.
문서가 원래 걱정했던 "청크당 10~20분 루프"(§7)가 사라진다 — **이게 강연으로 시작하는 진짜 이득이다.**

### 4-2. FILM (2단계 — 설계 보존)

```
30분 청크 (mp4) + SRT
  ├─[1] 자막 파싱 ─────────────── LLM 0회
  ├─[2] 샷 검출 (scdet) ────────── LLM 0회, 컷 후보
  └─[3] 씬 분할 ──────────────── [1]+[2] 병합. LLM 0회 (또는 경계 검증만)
  ─[4] 씬 해설 (Gemini, 영상 인라인) ─ 화면 정보 중심
  ─[5] rank → [6] 구간 잘라내기 → [7] 리프레이밍 + 렌더
```

### [1] 대사 확보

- **LECTURE**: faster-whisper **`small` + initial_prompt**(도메인 어휘). large-v3 는 쓰지 않는다 — 근거는 §7 실측표
- `language="ko"` 고정 · `vad_filter=True`(강연은 침묵이 길고 whisper 는 무음에서 환각한다)
- 청크는 **16kHz mono wav** 로 뽑는다 — whisper 가 내부에서 어차피 이 형식으로 리샘플하고,
  오디오 재인코딩은 샘플 단위로 정확해서 영상 복사의 키프레임 스냅 문제가 아예 없다.
  5분 추출 실측 0.2초 · 9.2MB (30분이면 ~58MB)
- 🔴 FILM 은 Gemini 에 영상을 넣어야 하므로 청크가 영상이어야 한다 — 여기서 갈라진다
- **FILM**: SRT/VTT 파싱 → `(start, end, text)`. 없으면 STT
- **이게 텍스트 척추다.** 강연에서는 사실상 콘텐츠 전부다

### [2] 샷 검출 — FILM 전용

- `ffmpeg scdet` 또는 PySceneDetect. 영화는 컷이 정직해서 잘 먹는다
- 🔴 강연에서는 쓰지 않는다. 고정 카메라라 경계가 안 나온다

### [3] 구간 분할

- **LECTURE**: 트랜스크립트를 Gemini 에 넣어 **주제 전환 지점**을 찾는다.
  출력은 `{start_idx, end_idx, summary}` 배열이고 **전부 발화 인덱스**다. 초는 `[1]`의
  타임스탬프에서 되찾는다(§12). 구간별 요약을 같은 호출에서 받아 `description` 에 넣는다 — 공짜다
- 응답은 `response_schema` 로 JSON 을 강제한다. 편의가 아니라 런타임 동작 때문이다 —
  "JSON 이 깨져서 재시도"라는 실패 경로가 사라지고, 남는 검증은 **내용**뿐이다
- **검증(§12)**: 존재하는 인덱스만 쓸 것 · 0 에서 시작해 마지막 발화에서 끝날 것 ·
  빈틈도 겹침도 없을 것. 하나라도 어기면 세그먼트를 만들지 않는다 —
  🔴 빈틈을 통과시키면 그 발화들은 rank 후보에서 조용히 빠지고, 결과물만 봐서는
  원래 없던 건지 잃어버린 건지 구분할 수 없다
- 🔴 이 단계는 **기준 중립**이어야 한다(§3). 프롬프트가 평가어를 금지하고 있고,
  그 금지 자체를 테스트로 고정했다
- **FILM**: 샷 경계 + 자막 공백 교차. 최소 씬 길이 30초로 시작
- **구간 = 주제·상황 단위. 카메라 컷 단위가 아니다**

### [5] rank

- 입력: 전 구간 요약 + 대사 + **작품/강연 맥락** (자립성 판단용)
- 출력: 순위 + 점수 + 근거
- **자립성을 1차 관문으로.** "앞을 다 들어야 이해되는 구간"은 감점이 아니라 후보 제외
- 출력 파싱: **Segment ID 화이트리스트 검증** (존재하는 구간만 지목했는지)

### [6] 구간 잘라내기

구간이 3~8분이라 통째로 못 쓴다. 안에서 30~60초를 골라야 한다.

- 입력: 해당 구간의 발화 목록(인덱스 + 텍스트)
- 출력: 시작/끝 **발화 인덱스**, 근거
- **초는 반드시 발화 타임스탬프에서.** 모델이 말하는 초는 믿지 않는다
- 말 중간에 잘리지 않게 발화 경계로 스냅

### [7] 리프레이밍 + 렌더

```
16:9 원본 ─┬─> 확대·블러 → 배경 (9:16 꽉 채움)
           └─> 원본 비율 유지 → 중앙 오버레이
```
- ffmpeg 필터체인 한 줄로 가능. 피사체 추적은 나중에
- 원본에서 다시 자른다 (분석용 저화질본이 아니라)
- ✅ **자막을 번인한다**(§9-9 확정). 9:16 으로 만들면 위아래 블러 영역이 완전히 비고,
  강연은 말이 콘텐츠 전부라 그 자리를 자막이 채워야 한다
  - 🔴 **발화를 그대로 한 장으로 쓰지 않는다.** 발화는 평균 4초·최대 11초라 글자가 너무 많다.
    word-level 타임스탬프로 다시 쪼갠다(최대 32자·4초) — `word_timestamps` 를 켜둔 실제 쓸모다
  - 시각은 **클립 시작 기준 상대 초**다. `-ss` 로 잘라낸 뒤의 타임라인에 얹히므로
    절대 초를 쓰면 전부 어긋난다
  - ASS + libass(`ass` 필터). 상단정렬(`\an8`) + MarginV 1300 이라 영상(656~1264) 아래에서
    시작해 아래로 자란다 — 두 줄이 돼도 화면을 가리지 않는다
  - 🔴 **Homebrew 기본 `ffmpeg` 에는 libass 가 없다**(운영 Docker 의 데비안 ffmpeg 에는 있다).
    `SHORTS_FFMPEG` 로 빌드를 지정한다(macOS: `brew install ffmpeg-full`).
    `sm doctor` 가 확인하고, 렌더는 조용히 자막을 빼는 대신 이유를 말하고 멈춘다

## 5. 데이터 모델

```python
Source                         # (구 Movie)
  id, title, content_type      # 'LECTURE' | 'FILM'   ← 파이프라인 분기의 근거
  path, duration_sec
  origin                       # 어디서 가져왔나 (URL/설명). 권리 감사용 — 잃으면 못 되찾는다
  fingerprint                  # 원본 식별자. DB 유니크 제약 필수
  context                      # 줄거리/강연 개요 (rank 의 자립성 판단용)
  created_by_admin_id          # 누가 등록했나. backend admins.id (FK 없는 숫자)
  status, error                # ingest 잡 상태

Chunk
  id, source_id, index, start_sec, end_sec, path
  # LECTURE 는 소스당 1개(전체 구간). 지금 안 만들면 FILM 도입 때 전 Segment 를 옮겨야 한다

Utterance                      # ← 중립 자산. STT/자막 원문의 정본
  id, chunk_id, idx
  start_sec, end_sec           # 🔴 소스 절대 초
  text, words                  # words = word-level 타임스탬프 JSON
  avg_logprob, no_speech_prob  # whisper 환각 탐지용 신호

Segment                        # ← 중립 자산 (구 Scene)
  id, chunk_id, index
  start_sec, end_sec
  description                  # LECTURE: 주제 요약 / FILM: 화면 해설
  start_utterance_idx          # 🔴 발화를 복사하지 않고 범위로 참조한다 (§9-11 결정)
  end_utterance_idx            #    start_sec/end_sec 은 이 범위에서 파생된 비정규화 값
  describe_model               # 어느 모델이 만들었나 (품질 편차 추적)
  describe_failed              # 실패 시 True. 조용한 누락 방지
  excluded_by                  # enum: null | 'human' | 'auto'  ← 빈 문자열로 구분하지 말 것
  excluded_reason

Run                            # ← 주관
  id, source_id
  criteria_prompt              # §6-1 의 [가변] 부분만
  prompt                       # 실제로 보낸 프롬프트 전문 — [고정] 부분도 튜닝되므로 필수
  ranked                       # 순위·점수 원문 + 파싱 결과
  requested_by_admin_id        # 누가 언제 돌렸나
  status, error, created_at

Clip
  id, run_id, segment_id
  start_sec, end_sec, score, reason
  path, rendered                # 편당 재개용 플래그

ClipReview                     # ← 품질 측정 (§11)
  id, clip_id, admin_id, verdict, note

StageCall                      # ← 계측. 첫날부터 넣는다 (구 LLMCall)
  id, source_id, run_id, segment_id     # 셋 다 nullable — [3]은 run/segment 이전에 돈다
  stage                        # ping | chunk | stt | segment | describe | rank | cut | render
  model, input_tokens, output_tokens, thinking_tokens   # LLM 단계에서만 채워진다
  latency_ms, error
  # 🔴 LLM 호출만이 아니라 모든 단계를 기록한다. §7 의 실제 제약은 비용이 아니라 시간인데,
  # LLM 만 기록하면 stt/render 소요 시간이 어디에도 안 남아 §9-8 실측이 불가능하다
```

### 왜 Utterance 가 별도 테이블인가 (문서 원안에는 없었다)

발화를 `Segment.dialogue` JSON 안에만 두면 **인덱스 좌표계가 둘로 갈라진다** —
`[3]` 은 청크 기준 발화 인덱스로 경계를 말하고, `[6]` 은 세그먼트 기준 인덱스로 구간을
말하게 된다. 둘을 오가는 변환이 생기는 순간 off-by-one 이 조용히 들어온다.

발화를 1급 행으로 두면 두 단계 모두 **"존재하는 idx 중 하나를 고르는 문제"**가 되고,
§12 가 요구하는 화이트리스트 검증이 `select idx from utterances where chunk_id = ?`
한 방으로 끝난다. STT 는 재생성에 CPU 분 단위가 드는 가장 비싼 중립 자산이기도 해서
§3 의 "중립 자산은 DB 에 캐시" 원칙에 가장 잘 맞는다.

### 첫날에 반드시 넣을 것 (나중에 넣으면 비싼 것들)

판단 기준은 "미래에 쓸 것 같은가"가 **아니다**. 나중에 넣는 비용이 지금보다 비싼가다.
비싼 경우는 셋뿐이다 — ① 전 쿼리를 고쳐야 하거나, ② 이미 들어온 나쁜 데이터를 되돌릴 수
없거나, ③ 지금 안 모으면 영영 복원 못 하는 관측 데이터거나.

- `content_type` — ① 파이프라인 분기의 근거. 나중에 넣으면 전 쿼리 수정
- `created_by_admin_id` / `requested_by_admin_id` — ① 나중에 넣으면 전 쿼리 수정
- 원본 파일 식별자에 **DB 유니크 제약** — ② 중복 유입은 복구 불가한 데이터 오염
- `excluded_by` enum — ② 빈 문자열로 사람/자동 구분하면 파싱 실패 시 영구히 안 풀림
- `StageCall` 테이블 — ③ 토큰과 **소요 시간**. 지금 안 모으면 처음부터 다시 모아야 함
- `sources.origin` — ③ 출처를 잃으면 사후 권리 감사가 불가능하다(§9-5)
- `runs.prompt` — ③ [고정] 프롬프트가 튜닝되면 run 간 비교가 무의미해진다. §11 의 전제

### 반대로, 지금 **안** 만드는 것 (그리고 왜)

나중에 nullable 컬럼 하나 더하는 건 A 단계에선 `sm db reset` 한 번이라 사실상 공짜다.
반면 **형태를 모르는 채 만든 테이블은 코드를 그 형태에 맞춰 끌고 간다** — 비어 있는 테이블은
"이미 설계된 것"처럼 읽혀서 다음 사람을 오도한다.

| 안 만드는 것 | 이유 |
|---|---|
| `shots` 테이블 (FILM `[2]`) | 샷 경계를 어떻게 쓸지가 §9-1 미정. 지금 만들면 틀린 형태를 굳힌다 |
| `signals` 수치 트랙 | 무슨 수치인지 아직 모른다(§3에 자리만 표시) |
| 자막 번인 관련 필드 | §9-9 미정. A7 결과를 보고 정한다 |
| `sources.subtitle_path` (FILM SRT) | 거의 확실히 필요하지만 나중에 넣는 비용이 0이다 |
| 태그·공개여부·조회수 등 | 요구사항이 없다 |

## 6. 기준 프롬프트

### 6-1. 구조

기준 프롬프트는 rank 단계에만 들어간다. 구간 분할/요약은 건드리지 않는다.

```
[고정] 자립성 관문 — 앞을 봐야 이해되는 구간은 후보에서 제외
[고정] 출력 형식 — Segment ID, 점수(100점 절대 기준), 근거
[가변] 기준 ─────────────────────── criteria_prompt
```

### 6-2. 여러 기준을 돌리는 게 싸다

중립 자산이 캐시돼 있으므로 rank 만 다시 돌리면 된다. 입력이 텍스트 수만 토큰뿐이라
**호출당 1센트 수준**. 초기에 일부러 여러 기준을 돌려보는 게
"내 중립 자산에 뭐가 빠졌나"를 알아내는 가장 싼 방법이다.

시작 기준 후보 — **LECTURE**:
- 핵심 논지 — 강연 전체를 한 구간으로 요약한다면
- 반전·통념 깨기 — 청중의 상식을 뒤집는 순간
- 인용 가능한 한 문장 — 그 자체로 성립하는 말
- 구체적 사례·비유 — 추상 개념을 잡아주는 대목

시작 기준 후보 — **FILM**: 액션·격돌 / 감정 폭발 / 명대사 / 반전·폭로

### 6-3. 빈 지시문을 남기지 않는다

기준 문자열이 비면 **그 줄 자체를 프롬프트에서 뺀다.**
빈 지시문을 남기면 모델이 그걸 해석한다.

## 7. 비용 · 성능 기준선

### 7-1. LECTURE (1단계 실제 비용)

| 단계 | 입력 | 비용 |
|---|---|---|
| STT | 로컬 CPU | $0 (시간이 비용) |
| `[3]` 주제 분할 | 트랜스크립트 ~1만 토큰 | 센트 미만 |
| `[5]` rank | 구간 요약 ~2천 토큰 | 센트 미만 |
| `[6]` 구간 잘라내기 | 발화 목록 ~2천 토큰 | 센트 미만 |

**비용은 제약이 아니다. 실제 제약은 STT CPU 시간이다.**

**실측 (2026-08-29, M계열 Mac · CPU · int8 · 5분 오디오 · VAD on · language=ko)**

| | `small` | **`small` + initial_prompt** | `large-v3` |
|---|---|---|---|
| 추론 | 32.8s (9.1x 실시간) | **32.1s (9.4x)** | 323.0s (0.9x) |
| 추론 중 RSS | 1.11 GB | **1.11 GB** | 3.4 GB |
| 모델 파일 | 464 MB | 464 MB | 2.9 GB |
| 고유명사 오류 | `이체` 1회 | **0회** (`니체` 5/5) | `닐체` 4 + `칸토` 1 |
| 발화 수 | 80 | 62 | 55 |
| 발화 길이 평균/최대 | 3.1s / 6.8s | 4.1s / 11.3s | 5.0s / **19.5s** |
| 음성 커버리지 | 83% | 85% | 91% |

**→ `small` + initial_prompt 를 쓴다. 개발·운영 모두.** 문서가 원래 가정했던
"개발은 small, 최종은 large-v3" 는 **틀렸다.** 근거 셋:

1. **large-v3 가 고유명사에서 더 나빴다.** `니체`를 `닐체`로 4회, `칸트`를 `칸토`로 1회
   흘렸다. small 은 1회 틀렸고, initial_prompt 를 주자 0회가 됐다. 이 단어들은 `[5]` rank 의
   판단 재료라 흘리면 안 된다
2. **10배 느리다.** 0.9x 실시간이면 30분 청크에 33분이 걸린다 — §7 이 "실제 제약은 시간"
   이라고 한 그 제약을 정면으로 때린다
3. **발화가 너무 길다.** 최대 19.5s, 10초 초과가 7개다. `[6]` 이 "발화 경계로 스냅"할 때
   (§4-[6]) 30~60초 클립에 스냅 지점이 두세 개밖에 안 생긴다

부수적으로 **4GB VM 문제도 사라진다** — small 은 추론 중 1.11GB 라 기존 VM 에 들어간다.
large-v3 는 3.4GB 라 app(1300m)+pg(512m)+redis(320m) 위에 얹을 수 없었다.

> ⚠️ 5분 샘플 1건의 결과다. 속도·메모리·발화 길이는 표본과 무관하지만, 고유명사 정확도
> 차이는 표본이 작다. 다른 구간에서 재확인할 것.

**initial_prompt 는 어휘 나열로 짧게.** 길면 모델이 그 문체를 따라 하며 없는 말을 만든다.
쓴 프롬프트는 `stage_calls.params` 에 남는다 — 안 남기면 변형끼리 비교가 불가능하다.

### 7-2. FILM (2단계 — 참고용 보존)

Gemini 는 영상을 1 FPS 로 샘플링: 프레임 258토큰/장(기본) 또는 66토큰/장(`media_resolution=low`),
오디오 32토큰/초 → 합계 ≈ 초당 300토큰(기본) / 100토큰(low).

| 설정 | 입력 토큰 | 비용 (3.6 Flash) |
|---|---|---|
| low + 무음 | 119k | ~$0.09 |
| low + 오디오 | 176k | ~$0.13 |
| 기본 해상도 | 540k | ~$0.41 |

30분당 200~700원. 2시간 영화 통째로도 $2 안쪽. 실제 제약은 **청크당 10~20분의 처리 시간**이다.

### 공통

| 항목 | 내용 |
|---|---|
| thinking 토큰 | 사고 과정이 출력 토큰이고 단가가 입력의 5배라 여기서 튄다. `sm doctor` 가 매 호출 값을 보여준다 |

| DB | SQLite → PostgreSQL (C5) | 운영은 backend 의 기존 postgres 인스턴스에 **별도 DB** |
| LLM | Gemini (`google-genai` 2.20.0) | Files API 는 FILM 단계에서 필요 |
| 영상 | **ffmpeg/ffprobe 9.0.1 바이너리 + subprocess** | 파이썬 영상 라이브러리 안 씀 |
| 자막 | ASS + **libass** (`ass` 필터) | 🔴 Homebrew 기본 ffmpeg 엔 없다 — `SHORTS_FFMPEG` 로 지정 |
| 샷 검출 | ffmpeg scdet 또는 PySceneDetect | FILM 단계에서 결정 |
| STT | **faster-whisper** (`uv sync --extra stt`) | 기본 설치에서 제외 — 무겁다 |

**영상 처리는 전부 subprocess.** moviepy 계열은 쓰지 않는다 — 느리고 ffmpeg 옵션을 다 못 쓴다.

### 왜 backend(Java) 안이 아닌가

Java 단일 레포도 검토했다(ffmpeg 는 subprocess 라 동일하고 Gemini 도 REST 로 가능).
파이썬 별도 레포로 정한 근거:

1. **STT 타협이 사라진다** — Java 였다면 faster-whisper 를 못 써서 Gemini STT 로 대체해야 했고,
   그러면 §12 의 "초는 LLM 에서 받지 않는다"가 흔들린다. 파이썬에서는 그 타협이 없다
2. **탐색 루프 속도** — v1 은 프롬프트를 고치고 결과를 보는 작업의 반복이다(§10). 스크립트
   재실행이 JVM 재빌드보다 빠르고, §9 의 미정 항목 대부분이 이 루프에서 풀린다
3. **리소스 격리** — 운영 VM 은 4GB 다(app 1300m / pg 512m / redis 320m). 같은 JVM 에서
   영상을 처리하면 무거운 잡 하나가 API 를 끌고 들어간다. 컨테이너를 나누면 벽이 생긴다
4. **결합도가 원래 낮다** — 도메인 테이블과 FK 가 0개고 admin id 만 걸친다. 분리 비용이
   가장 싼 종류이며, 베타가 접히면 레포를 지우면 끝난다

## 12. 코딩 규약

- **영상 처리는 subprocess 로 ffmpeg 직접 호출.** 라이브러리 래퍼 금지
- **초 단위 정밀도가 필요한 값은 파일명 또는 발화/자막 타임스탬프에서.** LLM 이 말한 초를 그대로 쓰지 않는다
  - LLM 에게는 **인덱스**를 고르게 하고, 초는 우리가 되찾는다
- **LLM 출력은 항상 검증한다.** Segment ID 화이트리스트, 점수 범위, 파싱 실패 시 재시도
- **모델에게 "하지 마라"고 지시하는 대신 입력에서 뺀다**
- **실측 근거는 주석에 남긴다.** 왜 이 숫자인지, 어떤 사고가 있었는지
  - `🔴` 치명적 주의사항 / `TODO:` 향후 개선 여지
  - ⚠️ backend 레포는 Java 주석을 금지하지만 **shorts_maker 는 반대다.** 레포가 다르다
- **모든 단계는 `stage_calls` 에 기록.** 예외 없이 — LLM 호출뿐 아니라 stt/render 도

## 13. 서비스 경계 · 배포

**shorts_maker 는 독립 서비스다.** 프론트와 API 가 한 레포·한 컨테이너·한 오리진에 있다.

```
인터넷 ──443──> nginx ──127.0.0.1:8100──> shorts 컨테이너
                                            ├── FastAPI  /api/**, /auth/**
                                            └── web/dist  /  (같은 오리진에서 서빙)
```

### 어떻게 여기까지 왔나

> **2026-08-30**: 원래는 admin-web 이 shorts_maker 를 직접 호출하고 두 서비스가 `JWT_SECRET`
> 을 공유하는 설계였다. **backend(Spring) 프록시로 바꿨다** — 시크릿 공유가 사라지고
> shorts_maker 는 JWT 를 모르게 됐다. 대가는 backend 의 프록시 엔드포인트뿐이었다.
>
> **2026-09-03**: **프록시도 걷어내고 완전히 분리했다.** SWYP 조직의 3개 레포(backend ·
> admin-web · shorts_maker)에서 이 파이프라인만 떼어냈다. 이유는 미래 대비가 아니라 이미
> 내고 있던 비용이다 — 설계 문서가 남의 레포에 있었고, backend 는 순수 통과용 Java 파일
> 13개를 지고 있었고, 프론트의 blob URL 우회는 오직 프록시 때문에 존재했다.
>
> 그 결과 바뀐 것:
> - 관리자 인증을 **여기서 한다**(§13-1). Spring 이 대신 해주던 일이 사라졌다
> - `/admin/shorts/**` → `/api/**`. `ApiResponse<T>` 봉투도 함께 사라졌다
> - `created_by_admin_id` · `requested_by_admin_id` · `clip_reviews.admin_id` 삭제(스키마 v8).
>   backend 의 `admins.id` 를 담던 값이라 독립 후에는 참조할 곳이 없다
> - 클립을 `<video src>` 로 바로 튼다 → **브라우저가 range 요청으로 스트리밍**한다.
>   예전엔 Authorization 헤더 때문에 blob 으로 통째로 받아야 첫 프레임이 나왔다

### 13-1. 인증

**비밀번호 1개 + 서명된 httpOnly 세션 쿠키.** `backend/src/shorts_maker/auth.py`.

- **회원가입은 없다.** 운영자 1명이 쓰는 도구다. 사용자 개념을 넣는 순간 ① 모든 테이블에
  소유자 스코프 ② 워커 1개짜리 잡 큐가 사용자 간 공유 병목 ③ 사용자별 Gemini 비용 한도가
  따라온다. 두 번째 사용자가 실제로 생길 때 할 일이다
- 세션 서명 키는 비밀번호에서 파생한다(HMAC). **비밀번호를 바꾸면 기존 세션이 전부 무효** —
  유출됐을 때의 유일한 회수 수단이다
- 로그인 실패 5회면 60초 잠근다. 카운터가 IP 별이 아니라 **전역**인 건 절충이다 — IP 를
  돌려가며 우회하는 걸 막는 대신 공격자가 운영자를 잠글 수 있다. 1인용 도구에서는 뚫리는
  쪽이 더 나쁘다
- `X-Shorts-Token` 은 **기계 클라이언트용으로 남겨뒀다**(선택). 브라우저는 쿠키를 쓴다

🔴 **전제를 코드가 강제한다**: 루프백이 아닌 주소에 바인딩하면서 `SHORTS_ADMIN_PASSWORD`
가 없으면 기동을 거부한다(`api.check_binding`). 설정 실수로 무인증 인스턴스가 외부에
열리는 경로를 막는다. `tests/test_api_auth.py` 가 이 경계 전체를 지킨다.

### 13-2. 노출면

- `/health` — **무인증**. 도커 헬스체크와 nginx 가 쓴다. 🔴 설정값을 담지 않는다.
  프록시 뒤에 있을 때는 이 응답이 도커 네트워크 밖으로 안 나갔지만 지금은 인터넷에 열려
  있다 — 화면이 쓰던 모델명·스키마 버전은 `/api/status`(인증 필요)로 옮겼다
- `/api/**` · `/auth/me` 외 전부 인증 필요
- `/` 와 그 아래 — 빌드된 프론트. catch-all 이라 **반드시 API 라우트 뒤에 등록**한다.
  앞에 두면 `/api/**` 가 전부 프론트로 빨려 들어가고, 없는 엔드포인트가 index.html 로
  200 을 받아 프론트가 HTML 을 JSON 으로 파싱하다 엉뚱한 곳에서 죽는다

### 13-3. 배포

Naver Cloud 단일 VM(4GB / 2vCPU). `docker compose` 한 스택이고 nginx 가 앞에 선다.

| | 상한 | 비고 |
|---|---|---|
| shorts | 3000m | whisper `small` 추론이 실측 1.1GB + ffmpeg |
| 나머지 | ~1000m | OS · nginx · 빌드 순간 |

🔴 이 배분은 **이 VM 에 다른 워크로드가 없다는 전제**다. backend 와 같은 VM 을 쓰던
시절에는 1400m 였다 — 뭔가를 같이 얹으면 여기부터 다시 계산한다.

🔴 **2vCPU 라 잡 워커 1개가 특히 중요하다.** STT 와 ffmpeg 가 겹치면 API 응답까지 같이
느려진다. 동시 실행은 정책이 아니라 구조로 막혀 있다(§4).
